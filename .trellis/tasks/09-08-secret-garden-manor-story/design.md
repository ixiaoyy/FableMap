## 总体数据流

```text
玩家输入 / 有限剧情演出
        ↓ 明确的庄园动作或完成确认
GameSession.dispatch
        ↓ 在隔离候选中校验地点、人物、前置事件、工具和成本
庄园固定规则 + 既有 Inventory / WorldRules
        ↓ 完整状态校验
SaveRepository 原子保存
        ↓ 成功后发布；失败保留原状态与同一待重试候选
snapshot / 庄园派生视图
        ↓
地图门锁、花地、NPC 站位、对白、UI 和音效共同更新
```

- `GameSession` 始终是唯一可变玩法状态所有者。
- 章节完成、门是否开放、物品扣除不能来自动画结束后对 `_state` 的直接写入。
- 对话工具即使能执行任意脚本，也只通过批准的有限命令进入会话，不持有真实状态引用，不自行写文件或 IndexedDB。
- 素材帧、镜头插值、文字逐字显示和临时轮椅推行动画属于表现层，不写入玩法存档。

## 候选模块边界

| 候选位置 | 职责 | 不应承担 |
|---|---|---|
| `godot/data/manor_story.json` | 稳定章节/场景/人物/目标 ID、有限前置关系、地点引用 | 任意脚本、条件表达式解释器或通用任务语言 |
| `godot/domain/manor_rules.gd` | 本篇章动作校验、进度变化和只读派生结果 | 保存 IO、UI 或与原 NPC 重复的寻路算法 |
| `godot/presentation/manor_scene_player.gd` | 经选型确认后的有限场景播放、镜头和临时动作协调 | 第二套剧情进度、全局副作用或独立时间结算 |
| `godot/scenes/regions/manor-*.tscn` | 人工维护的场景包装与表现 | 手改 generated 内容或独占玩法碰撞真值 |
| 对话内容文件 | 人物台词、静态选择和文本 ID | 由文本随意指定解锁字段、数量或奖励 |

对话内容最终采用现有 JSON 形式还是某个固定插件格式，待 O05 决定。只能选一种对白内容权威来源；若选插件，领域事件登记与对白文本各自有明确职责，不能在两处维护同一前置条件。

项目专用的固定故事规则不需要变成通用引擎。对于对话编辑/播放等通用能力，必须先完成下节的开源对比，不因本文件列出候选文件名就直接自研。

## 持久状态候选

在新当前版本状态下考虑增加单一 `manorProgress`，字段最终在 O01/O02 后冻结。下表为结构建议，不是现有字段，也不指定下一版本号。

| 字段 | 候选类型与初值 | 含义和约束 |
|---|---|---|
| `completedBeatIds` | 有限唯一 ID 数组，空数组 | 已完成的必要剧情节点；ID 只能来自固定登记，前置闭包必须成立 |
| `discoveredClueIds` | 有限唯一 ID 数组，空数组 | 允许玩家回顾的信息，不提前收录未知人物与答案 |
| `gardenAccess` | `unknown / key-found / open`，初始 `unknown` | 钥匙发现与开门事实；与相应事件关系一致，不任意回退 |
| `gardenSites` | 固定目标 ID 到有限状态的字典 | 每个目标自己的整理/照料状态，初始化完整，不接受未知目标 |
| `lastCareDayBySite` | 固定目标到合法日序号或 `null` | 只有 O02/O03 确实需要跨日限制时才加入；不预设每日刷次数 |
| `pendingSceneId` | 已登记场景 ID 或 `null`，初始 `null` | 已开始但尚未提交终点的必要场景；恢复时从固定安全起点重播 |

章节名称、花园视觉阶段、科林可用姿态、主人是否归来及当前可播放场景从这些事实派生。原则上不再保存一份独立 `chapterIndex`、好感分数和行动能力布尔集合，避免互相矛盾。

钥匙建议作为剧情事实与可查看图标，不占普通可出售/丢弃的物品槽；这是待评审设计。若用户要求实体物品，需单独定义背包满、存箱、出售、丢弃和找回合同，不能简单放入普通物品表。

剧情角色日常位置由阶段与世界时间派生，临时镜头和逐字位置不保存。O01 若选择玛丽视角，必须增加明确的控制权及返回上下文设计，本表不得被当作已经覆盖该方案。

### 校验不变量

1. 所有 ID 都来自有限当前内容集合；数组去重且有条数上限，不接受任意未来 ID。
2. 后续必要剧情节点不能缺失前置；开门、出行和结局不能越级。
3. `gardenAccess == open` 与对应发现/完成记录一致，门视觉、出口权限和路径阻挡使用同一派生结论。
4. 花地只能使用本目标允许的状态；永久整理不会被日结再生写回初始值。
5. 待播放场景有合法前置、未完成且有有效起点；不能同时存在两个必要演出。
6. 日期、坐标、计数沿用当前数值校验习惯，正常化 JSON 数值后再验证，`null` 不能被当成零日。
7. 当前 `player.regionId` 和恢复点必须存在；不因为场景移除而静默瞬移到 Farm 掩盖错误。
8. 新故事角色不破坏原八名居民的严格集合校验，不为填满旧字段而伪造送礼记录。

## 候选命令与效果

名称在实施前冻结；每个命令只接收动作意图，成本、结果和可解锁内容由本地固定定义决定。

| 命令 | 输入 | 主要校验 | 成功结果 |
|---|---|---|---|
| `inspect-manor-clue` | `clueId` | 所在区域、距离、可发现前置 | 必要时记录已知信息；重复查看只展示已有内容 |
| `unlock-manor-gate` | `gateId` | 合法门、距离、钥匙状态 | 开门与相关事实在同一候选提交 |
| `care-manor-site` | `siteId`、`actionId`、必要的工具选择 | 阶段、距离、目标状态、工具、已批准成本 | 一次整理/照料和必要消耗同时发生 |
| `talk-to-manor-npc` | `npcId` | 角色登记、当前出现、同区和距离 | 返回当前可知对白；有持久变化时走保存链 |
| `begin-manor-scene` | `sceneId` | 前置、人物、地点、无其他未完成演出 | 仅保存开始/恢复所需事实，成功后进入播放 |
| `complete-manor-scene` | `sceneId` | 匹配 pending、合法终点和未完成 | 提交剧情结果、必要终点位置并清空 pending |
| `defer-manor-scene` | `sceneId` | 当前场景允许暂离且匹配 pending | 回安全起点，保持未完成，释放临时播放状态 |

需要观察门但不改变状态时，不强行制造一次写盘。已有未完成保存期间不得开启另一项改变状态的命令；复用 `GameSession` 的锁定和重试行为。

`transition-region` 保持现有入口，补充本篇章条件门检查，不开第二条可绕过规则的直接传送路径。通行条件依据玩家实际处于出口，不能仅凭任意传入 `exitId`。

## 必要演出的开始、结束与恢复

建议采用固定安全节点恢复，不保存任意动画帧，也不引入通用事件日志或剧情事务平台。

1. 玩家到达并选择开始；会话确认人物/场景条件，保存 `pendingSceneId` 与合法起点状态。
2. 保存成功后，表现层建立有限人物临时站位，锁定世界操作并暂停世界时间；台词和动画只改变表现。
3. 最后一段对白或用户明确跳过后，发送匹配的完成命令。跳过须先给简短摘要，不能等同于真人已看完演出。
4. 终点只在保存成功后生效；角色日程、花园层与输入按新 snapshot 恢复。
5. 中途退出后，继续游戏发现合法 pending，从该场景固定起点重播，不叠加上次临时角色。
6. 若玩家暂离，使用允许的退出动作返回起点并清空 pending，但不写完成标记；该事件之后仍可重试。
7. 路径、资源或播放错误应终止本次临时演出并给出恢复入口，不依赖无限等待或默认成功结束。

开始场景不提前消耗故事材料；需要消耗的园艺行为由独立动作提交。这样重播不会多次扣材料，也不需要为每句台词设计撤销日志。

| 中断位置 | 必须看到的结果 |
|---|---|
| 开始保存之前/失败 | 不进入不可退出演出，原进度和位置有效 |
| 台词或动作中途退出 | 下次从合法场景起点重播，世界未越级 |
| 终点保存失败 | 仍未完成，提示重试同一候选，不重新计算奖励 |
| 完成保存后再次进入 | 不重播强制场景，使用完成后的世界 |
| 已打开背包或其他菜单 | 不叠加第二套焦点，不让底层角色继续用工具 |

## 地图、动态阻挡与花地

- 地图来源是 `public/map/*.tmj`，Godot 准备脚本枚举输入并生成目录。新区域要同时检查 decoder 允许的属性、catalog 校验、初始状态和 `data/media.json` 的区域表现配置。
- 手工场景放 `scenes/regions/`；`generated/`、`media/` 和 `.godot/` 不手改。
- 装饰层不能单独成为玩法碰撞真值。静态不可通行区域仍由地图掩码提供，门与未整理路径的动态阻挡由同一领域规则提供。
- 现有 NPC A* 使用静态掩码与动态角色，新增门后需接入相同动态阻挡，不允许 NPC 穿过玩家无法通过的门。
- 固定花床不写入硬编码 `farm:*` 的 `farmTiles`。庄园花床由本篇章有限状态投影，避免将整个农田系统泛化。
- 地面清理目标使用稳定 ID；不把全部剧情障碍登记成默认会再生的普通树木。
- 室外照明、雨风与声音当前按四个区域 ID 判定，必须明确新增区域的室内/室外配置，不能让庄园花园误用室内效果。
- 不预设地图格数、出口坐标或角色缩放，先在当前相机尺度制作空间草图与轮椅路线样板。

## 新人物与现有居民的接入

- 增加有限庄园人物登记，区分世界可见人物、记忆中的人物和环境动物。
- 原有八名居民保持当前 profiles、friendships、npcDialogue、委托和营业规则；庄园人物不默认加入这些集合。
- 世界渲染和互动查找需能读取庄园人物的名字、精灵、动作与对话归属，不能只改某一张日程表。
- 复用现有 NPC 运动组件的寻路与避让，增加本篇章阶段目标输入；已有普通日程与演出临时站位的优先级写清楚。
- 场景临时站位优先于庄园日常，庄园日常由章节事实与世界时间派生；暂停演出时普通日程不另行推进。
- 轮椅采用固定方向和推行组合动画，路线按组合占地检查；先解决实际门宽与转角，不引入刚体轮椅模拟。
- 动物只使用必要停留点与有限运动，不接入玩家宠物领养、养成、战斗或寻宝系统。

## 存档版本与原子性

当前封套版本与玩法版本分别为 `1` 和 `13`，不得混为一个数字。实施时明确本任务改变哪层版本并同步初始状态和 codec；现在不选择或改写下一版本号。

- 继续使用独立 Godot Web 存储与 Windows 原子文件；本篇章不再建立一份并行故事存档。
- 新增资源/NPC/目标会触及严格集合校验，需要一次协调变更，不能给旧状态静默补字段假装兼容。
- 按项目开发档政策，从用户明确清理/新建的当前版本档进行验收；不做旧开发档迁移、备份或自动清理。
- 保存失败复用 `_pending` 同一候选重试；不能在重试时重新推进天气、材料或章节。
- 离开庄园、日结与普通移动检查点不得覆盖未提交的关键剧情结果，顺序沿用会话已有协调机制。
- 数据库、身份、论坛和旧 Phaser 存档不在此策略范围内，不连接或修改它们。

## 风险与处理顺序

| 风险 | 处理方式 |
|---|---|
| 玩家视角未定导致剧本返工 | O01 在对白、身份状态和完整美术定稿前收敛 |
| 完整故事退化成刷材料任务 | 每章先验收人物行动和环境变化，再定数值 |
| 大地图或动画投入过早 | 先做 C02 的发现与 C05 的轮椅/同框样板，完整范围仍保留 |
| 单独改视觉引起碰撞和路径不一致 | 领域投影共享动态阻挡，图层与出生点一起复核 |
| 场景中断或保存失败卡住 | 用固定起点与单场景 pending，复用候选保存，不构建新事务框架 |
| 插件接管变量和保存 | 只暴露只读条件与有限会话命令，选型不通过就记录拒绝理由 |
| 新人物污染旧社交集合 | 领域归属分开，渲染层合并展示，单独核对原居民路径 |
| 文学内容与现实素材来源混淆 | 分开登记原著、中文改编、视觉与音频来源，采用项逐一确认 |

## 回退与发布边界

本轮只写规划；撤销范围仅是本任务的新文件，撤销前检查完整 diff，不能覆盖其他改动。

未来代码回退需基于已批准基线精确撤销本篇章改动；新增当前版本档可能无法由旧程序读取，不能承诺通过回退保留进度。正式媒体一经上传使用不可变 key，通过清单切换版本，不覆盖原对象。以上是设计边界，不构成当前回退、上传或发布授权。
